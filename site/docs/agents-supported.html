Available today

Claude Code and Codex both have everything in these docs (Pi and Antigravity CLI have their own sections below): terminals, the connecto command, automations, packages, isolated and system profiles, history, and remote sessions.

  • Connecto does not pin a CLI version. It relies on the tools staying compatible, and runs its own verified copy, made from your install at the first launch. To pick up a newer version by hand, run connecto-app provision.
  • The tools' own auto-update is turned off inside Connecto, so a session never changes under you.
  • Writing a new package with an agent's help uses Claude. Titles use Claude too.

Pi, with the model provider you choose

Pi is an agent CLI that is not tied to one vendor. In Connecto it has its own terminals, the connecto command (so it can ask Claude or Codex, and be asked), history and resume, and the same Pause and audit log.

  • Choose it at the first launch, or add it in Settings > Agents. Either way, Connecto runs Pi's own installer from pi.dev, on macOS and on Windows. Pi needs Node.js 22.19 or newer: if it is missing or older, Connecto asks, then installs Node.js 22 from nodejs.org in your own folder (~/.local/share/pi-node on a Mac, %LOCALAPPDATA%\pi-node on Windows), without touching a Node.js you already have. A pi you installed yourself is found where it is.
  • Set up a provider with Set up model providers… on Pi's card: an API key for OpenRouter or Together AI, or the address of a local LM Studio server. Keys are kept in Connecto's secret store and given to a Pi terminal only in its environment. The local server is checked when you save its address, and found by itself when it listens on another port.
  • Pi is offered once a provider works: a saved key, or a local server that answers with a chat model. The New terminal chooser then shows which ones it has, such as Together AI | OpenRouter | Local.
  • Choose the model when you open the terminal. The chooser has a model field for Pi: type to find one among every model your providers offer, or leave it empty for the default set in the same dialog. An agent chooses with connecto add pi --model <provider>/<model>. Inside Pi, /model changes it at any time.
  • Local models load on demand. Every model you downloaded in LM Studio is listed under lmstudio/, loaded or not, and LM Studio loads one at the first message.
  • A project's Tools can be Claude, Codex, Pi, Antigravity or All.

Where Pi differs from the other two:

  • No verified copy. Pi is a Node.js program published without a code signature, so Connecto runs it where it is installed.
  • No permission prompts. Pi never asks before a tool call. Settings > Launch only decides whether a project's own .pi resources load without asking.
  • There are no automations for Pi's screens, and project memory does not capture Pi's turns yet.

Antigravity CLI

Antigravity CLI (agy) is Google's coding agent, on Gemini models, and the successor of Gemini CLI. In Connecto it has its own terminals, the connecto command (so it can ask Claude, Codex or Pi, and be asked), history and resume, and the same Pause and audit log.

  • Choose it at the first launch, or add it in Settings > Agents. Connecto runs Google's official installer from antigravity.google, on macOS and on Windows. It puts agy in ~/.local/bin (%LOCALAPPDATA%\agy\bin on Windows). An agy you installed yourself is found where it is.
  • Sign in inside its terminal, with your Google account, or give it a GEMINI_API_KEY.
  • Your own settings. Antigravity always uses your own ~/.gemini: it has no way to be pointed at another folder, so there is no isolated profile for it.
  • Its turns are reported by hooks. Connecto keeps one entry, named connecto, in ~/.gemini/config/hooks.json, and leaves your other hooks as they are. Outside a Connecto terminal it does nothing.
  • Settings > Launch: skip permission prompts (--dangerously-skip-permissions), auto mode where your account offers it (--mode auto), or its normal prompts.

Where Antigravity differs from Claude Code and Codex:

  • No verified copy. agy updates itself, so Connecto runs it where it is installed, as it does Pi.
  • A permission prompt is not reported. Antigravity has no hook for it, so a terminal waiting at one is not marked as needing you. An interrupted turn ends as finished.
  • It was built from Antigravity's documentation, not yet tried with a signed-in account. There are no automations for its screens, and project memory does not capture its turns yet.

OpenCode

OpenCode (opencode) is an open coding agent on any provider's models, with free ones of its own. In Connecto it has its own terminals, the connecto command (so it can ask the other agents, and be asked), history and resume, and the same Pause and audit log. Connecto supports the 1.x line, the one OpenCode's installer puts in ~/.opencode/bin.

  • Choose it at the first launch, or add it in Settings > Agents. Connecto runs OpenCode's official installer from opencode.ai, and leaves your shell's startup file alone; on Windows it installs OpenCode's own release from GitHub into ~\.opencode\bin. An opencode you installed yourself is found where it is. Only OpenCode 1.x is supported: an OpenCode 2 is refused with how to install 1.x.
  • Sign in inside its terminal: type /connect and pick a provider. Its free models need no sign-in at all.
  • Your own settings, or the project's. By default it uses your own OpenCode folders. With its config set to Isolated in the project's settings, the project has its own OpenCode settings, sign-ins and sessions; the commands the agent runs still see your own folders.
  • Its turns are reported by a plugin that Connecto loads for its terminals only. Nothing is written into OpenCode's folders, and your own plugins still load.
  • Settings > Launch: approve every permission your config does not deny (--auto), or its normal prompts. --model takes provider/model; there is no --effort.

Where OpenCode differs from Claude Code and Codex:

  • No verified copy. OpenCode upgrades itself, so Connecto runs it where it is installed.
  • An interrupted turn ends as failed, not as interrupted. There are no automations for its screens, and project memory does not capture its turns yet.

A plain shell

Besides the agents, a terminal can be your login shell: $SHELL started as an interactive login shell in the project folder, so it has the environment you know. It has no turns, no login and no launch mode, so its dot is a small grey square that only says it is running. Other terminals drive it with connecto send <id> '<one command line>' and connecto read <id>; --ask and watch are refused, because a shell has no end of turn to report. It is held to the same rules as any terminal: Pause blocks writes, and every write is in the audit log. It is also as powerful as a bypass-permissions agent, so treat access to it that way.

The aim is for a new agent to be a full member of the workspace, not a second-class terminal:

  • its own terminals, in the same project tree, with the same states;
  • the connecto command, so it can ask the other agents for help, and be asked;
  • the same Pause, audit log and redaction;
  • a place in packages, automations and per-project settings, as far as each tool allows.

How far each one goes depends on what the CLI itself offers: for example, whether it reports the end of a turn, and whether it can resume a conversation.

What an adapter does

For each tool, an adapter tells Connecto how to:

  • launch it, with which options and which profile folder;
  • sign in, and tell whether it is signed in;
  • know when it is ready for input, when a turn starts and when it ends;
  • capture its reply, so send --ask can deliver it;
  • resume a conversation from the history.

Adapters are part of Connecto itself. A new agent arrives with a new version of the app.
