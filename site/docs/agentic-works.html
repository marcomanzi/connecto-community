Agentic Works

Agentic Works turns a project into a job queue. Any program that can write a row to PostgreSQL asks for a piece of work. An agent in the project does it, and the answer comes back in the same row as JSON that matches a schema you chose.

Use it to give agents work from things that are not you:

  • Your own app. A backend inserts "summarize this ticket" or "extract the fields from this invoice" and reads the result later.
  • Workflow tools and schedulers. n8n, a cron job, or a CI step inserts a job and waits for its row to finish.
  • Batches. Insert a row per file, page or customer and let the project work through them while you do something else.

The work runs in your project, with its files, its skills and plugins and its launch mode, on your own agent accounts.

How it works

  1. You link the project to a PostgreSQL database. Connecto creates a private connecto_works schema there.
  2. You publish work types. A work type is instructions with a {{prompt}} placeholder, and the JSON Schema of the answer. It can also have setup and prepare commands that Connecto runs itself.
  3. A producer inserts a job: the project name, a work type and a prompt.
  4. Connecto claims the job, runs the type's prepare command if it has one, opens a terminal in the project, and gives the agent the instructions with the prompt filled in.
  5. When the agent's turn ends, Connecto checks its final answer against the schema. It writes the JSON to the row, or the reason it failed, and closes the terminal.

Link a database

You need a PostgreSQL database that Connecto can reach, and a role that can create a schema in it. Connecto must be running, with the project open.

  1. In Settings → Secrets, add a secret under the project whose value is the connection string, such as postgresql://works@db.example.com/app. Under How it may be used, choose Agentic Works database. Only Connecto reads it; no terminal ever sees it.
  2. Open the project and choose Terminal → Agentic Works…. Under Database, choose PostgreSQL connection string and enter the secret's name. (For Google Cloud SQL, see below.)
  3. Click Create queue and link for a new database. Use Validate existing queue to link a database whose queue already exists, such as one this project was linked to before.
  • A project can link several databases, each under a name (such as dev, staging or production; a link made without a name is default). A queue belongs to one project and is linked under one name only. A work type serves every linked database unless it is published for a list of them.
  • A database on another machine must accept TLS with a certificate this Mac trusts. Only localhost and loopback addresses may connect without it.
  • The schema, its tables and its sequence must belong to the role in the connection string. Connecto refuses a queue where anyone else can write. Granting SELECT to other roles is allowed.

Google Cloud SQL

A Cloud SQL for PostgreSQL instance can be linked without opening it to this Mac's IP address. Under Database, choose Google Cloud SQL. Connecto then connects the way Google's Cloud SQL connectors and the Cloud SQL Auth Proxy do:

  • A Google identity authorises the connection through IAM (roles/cloudsql.client). The instance's Authorized networks list is not used, so the same Mac works from home, the office or a phone hotspot.
  • Each connection is mutual TLS. Connecto presents a short-lived client certificate issued by the Cloud SQL Admin API, and checks the server against the instance's own CA and the instance's name.
  • No proxy runs, and gcloud is not needed once it is set up.

The form asks for:

  • Instance connection name, such as my-project:europe-west2:my-instance, shown on the instance's Overview page in the Cloud console.
  • Database and Database user, and the user's Password. The password is kept in Connecto's vault, under the project, and never shown again. With Sign in to the database with IAM on, there is no password: the user is the service account's IAM user and Connecto signs in with an OAuth token.
  • Google credential: a Service account key (click Import key file…; the key goes into the vault, and Connecto offers to move the downloaded file to the Trash), or My gcloud login (your own gcloud auth application-default login, used while it is valid).
  • IP type: Public, Private or Private Service Connect. The private types work only while this Mac is on that network, through a VPN for instance.

Test connection reports each step on its own line: credential loaded (with the identity's email), instance found, ephemeral certificate issued, TLS to the server verified, signed in, and whether the queue schema is there. Then use Create queue and link or Validate existing queue as for any database.

How to set it up

The sheet shows these steps under How to set this up, filled in with what you typed and ready to copy. <PROJECT>, <INSTANCE>, <DB> and <USER> stand for your Google project, instance, database and database user.

1. Create a service account for Connecto (once per Google project):

gcloud iam service-accounts create connecto-agentic-works \
  --project=<PROJECT> --display-name="Connecto Agentic Works"
gcloud projects add-iam-policy-binding <PROJECT> \
  --member="serviceAccount:connecto-agentic-works@<PROJECT>.iam.gserviceaccount.com" \
  --role="roles/cloudsql.client"

2. Create its key and import it:

gcloud iam service-accounts keys create ~/Downloads/connecto-<PROJECT>.json \
  --iam-account=connecto-agentic-works@<PROJECT>.iam.gserviceaccount.com

Then click Import key file… and choose that file. Connecto keeps the key in its encrypted vault, and you can delete the downloaded copy.

3. Create the database role that owns the queue. Run this once, connected as an administrator of <DB> (Cloud SQL Studio in the console works):

CREATE ROLE <USER> LOGIN PASSWORD '<a long password>';
GRANT CREATE ON DATABASE <DB> TO <USER>;
-- Let your application write jobs without sharing its own credentials:
GRANT <USER> TO <your application's database role>;

Connecto accepts a queue only when the role it connects with owns it and no other role has write grants on it. Role membership is not a grant, so the application can still write jobs through it.

4. Make sure the Cloud SQL Admin API is enabled (it usually already is):

gcloud services enable sqladmin.googleapis.com --project=<PROJECT>

You do not need to add this computer's IP to Authorized networks: access is granted by the service account.

With Sign in to the database with IAM, the service account also needs the Cloud SQL Instance User role, the instance needs IAM sign-in turned on, and the database user is an IAM user:

gcloud projects add-iam-policy-binding <PROJECT> \
  --member="serviceAccount:connecto-agentic-works@<PROJECT>.iam.gserviceaccount.com" \
  --role="roles/cloudsql.instanceUser"
gcloud sql instances patch <INSTANCE> --project=<PROJECT> \
  --database-flags=cloudsql.iam_authentication=on   # keep the instance's other flags!
gcloud sql users create connecto-agentic-works@<PROJECT>.iam \
  --instance=<INSTANCE> --project=<PROJECT> --type=cloud_iam_service_account

--database-flags replaces the instance's flags: list the existing ones too. See them with gcloud sql instances describe <INSTANCE> --format='value(settings.databaseFlags)'.

The database user is then connecto-agentic-works@<PROJECT>.iam (leave Database user empty to use it). Grant it CREATE ON DATABASE as in step 3, and grant it to the application role.

With My gcloud login instead of a key, run only:

gcloud auth application-default login

Your own Google account needs roles/cloudsql.client on <PROJECT>. Connecto uses that login while it is valid. A service account key keeps working without it.

When it does not connect

  • "… needs the role Cloud SQL Client": grant roles/cloudsql.client on the project to that identity (step 1).
  • "Enable the Cloud SQL Admin API": run step 4.
  • "Instance … not found": check the project, region and instance in the connection name.
  • "The instance has no public IP": choose Private or Private Service Connect, and connect this Mac to that network.
  • "The server is not …": the server's certificate is for another instance. Connecto stops there.

Define a work type

In the same sheet, under Work types:

  1. Discuss. Name the type (such as summary), choose Claude or Codex, and click Open authoring session. A terminal opens where the agent asks what the work should do, what the prompt will contain and what JSON you need. When you agree, it replies with the instructions and the schema.
  2. Review. Back in Terminal → Agentic Works…, enter the same work type and click Import author reply. Read and edit the fields. The instructions must contain {{prompt}} and the schema must be a valid JSON Schema. The setup and prepare fields are optional: see Setup and prepare commands.
  3. Publish. Click Publish reviewed definition. If the type has a setup command, it runs first, and the type is published only when it succeeds. To change a type later, import or edit it again and click Replace published definition.

A small example. Instructions:

Read {{prompt}} and summarize it in three sentences for a new developer.

Schema:

{
  "type": "object",
  "required": ["summary"],
  "properties": { "summary": { "type": "string" } }
}

Connecto adds the schema to the prompt itself and asks for one JSON value as the final answer, so your instructions need not repeat it.

Setup and prepare commands

Some work needs the machine ready, or files made, before an agent can start: a Python environment, a tool such as ffmpeg, a video cut into pieces. A work type can name two commands for that. Connecto runs them, not the agent, so the agent needs no shell access and no approvals for them.

{
  "setup":   { "argv": ["tool/connecto_setup.sh"] },
  "prepare": { "argv": [".venv/bin/python", "tool/connecto_prepare.py"], "timeout_s": 900 }
}
  • setup runs when you publish the type, and again when you click Re-run setup next to the type. It runs in a shell terminal named setup <type> · <project>, in the agentic jobs project: the agentic jobs folder of your Connecto Home, which Connecto opens in the Connecto Internal sidebar group, next to Automations. Watch it there and answer it if it asks for something, such as a password. It has no time limit. If it succeeds, its terminal closes and the type is published; if not, the type is not published and the terminal stays open so you can read why. The sheet shows when setup last succeeded. Setup needs Connecto Home to be chosen in Settings.
  • prepare runs before each job, before the agent's terminal opens. It reads the job's prompt on standard input and must print one JSON value (at most 256 KiB). That JSON replaces {{prepared}} in the instructions. If it exits with an error, the job fails with the end of its error output as the reason, and no agent starts.
  • If prepare exits with code 75 (prerequisites missing), Connecto runs setup once more, in its terminal, and then prepare once more. This setup must finish within the job's 30 minutes.
  • prepare gets CONNECTO_JOB_ID, CONNECTO_WORK_TYPE, and CONNECTO_JOB_DIR: a new, empty folder under .connecto/works/ in the project for the job's files. The agent can read it, since it is inside the project. Connecto deletes it when the job ends, and deletes any left over the next time it starts.

The rules:

  • argv is a list of strings, never a shell line. Its first item is a program name looked up on PATH, such as ffmpeg, or a path relative to the project, such as tool/setup.sh. Absolute paths and .. are refused.
  • timeout_s limits prepare: 1 to 1800 seconds, 600 if left out. Prepare also stops when the job's 30 minutes run out. Setup has no limit, so it ignores timeout_s.
  • The instructions contain {{prepared}} exactly when the type has a prepare command.
  • Both run in the work type's project folder. Prepare gets only PATH, HOME, LANG and TMPDIR from Connecto's environment, so no secret reaches it; Pause, Stop and closing the project end it along with everything it started. Setup runs in your login shell, with the environment your shell's startup files give it, plus CONNECTO_WORK_TYPE; closing its terminal ends it.
  • argv items may not contain control characters, such as a line break.
  • Each run is written to the audit log with its exit code and duration, never its output.

These commands run with your rights, outside the agent's permissions. Read every argument before publishing. A command that names a file in the project runs whatever that file contains when the job starts, so treat changes to those files like changes to the type.

Queue a job

Insert a row with the project's name as the sidebar shows it, and a published work type:

INSERT INTO connecto_works.connecto_jobs (project_name, work_type, prompt)
VALUES ('My Project', 'summary', 'the README in this project')
RETURNING id;

Then read its outcome:

SELECT status, result, reason
FROM connecto_works.connecto_jobs
WHERE id = 42;

Always write the schema name: the table is connecto_works.connecto_jobs, not in public.

The columns

ColumnYou set itMeaning
project_nameyesThe project, by its name in Connecto. If you rename the project, update its pending rows.
work_typeyesA published work type.
promptyesWhat replaces {{prompt}} in the instructions.
session_clioptionalThe agent that does the work: claude, codex, pi or opencode. Blank or agy (the default) gives the project's Agent for jobs: Automatic uses Antigravity when the project can, and otherwise a stand-in (Codex, Claude Code, Pi or OpenCode, the first usable).
modeloptionalA model that agent accepts, such as sonnet. Empty or default uses the agent's default. Used when the job names its agent, or Antigravity runs it; an agent the project chose for jobs uses the model set there, and a stand-in its fixed model: Codex runs gpt-6.1-terra and Claude runs haiku, while Pi and OpenCode use their defaults.
effortoptionalA reasoning effort that agent accepts, such as low or high. Empty or default leaves it alone. Used when the job names its agent, or Antigravity runs it; a stand-in, or another agent the project chose for jobs, gets none.
statusnoSee below.
resultnoThe agent's answer, as JSON that matched the schema.
reasonnoWhy a job failed or timed out.
id, created_at, claimed_at, attemptnoKept by the database and by Connecto.

A job for Claude on a chosen model:

INSERT INTO connecto_works.connecto_jobs
  (project_name, work_type, prompt, session_cli, model, effort)
VALUES ('My Project', 'summary', 'docs/architecture.md', 'claude', 'sonnet', 'low');

Statuses

StatusMeaning
to_doWaiting to be claimed.
doingClaimed: an agent is working on it.
done_from_agentFinished. result holds the JSON.
failedEnded without a valid answer. reason says why.
timeoutNot finished within 30 minutes of being claimed.

Order and timing

  • About every five seconds, while Connecto runs, the project is open and nothing is paused, Connecto looks for a job.
  • Within each database, Connecto claims the newest available pending job for the project first.
  • A project runs one job at a time unless you raise Jobs at once in the sheet (1 to 32, or connecto works parallel <n>). With more, several jobs run side by side, from one database or several; the databases share the places fairly, and Connecto looks again as soon as a job ends.
  • Each job runs in its own terminal, named agentic_works_<id>_…, which appears in the project while it works. It is closed when the job ends.
  • A job has 30 minutes from its claim. A job whose agent leaves background work running is not finished until that work ends.

What ends a job early

  • Pause, Stop, closing the project, or closing its terminal.
  • The agent's CLI stops at an approval prompt, a choice on screen or a login. Nobody is there to answer it, so the job fails. Use a launch mode without prompts for projects that take jobs. (A question the agent asks you with connecto works ask is different: the job waits for your answer and goes on.)
  • The agent fails to start, its turn is interrupted, or the session ends.
  • The type's prepare command fails, times out, or prints something other than one JSON value.
  • The final answer is not JSON, or does not match the schema. The reason names where it did not match.

Connecto records each outcome on this Mac before writing it to the database. If the database cannot be reached, the outcome is delivered once it can. A job is never started again on its own: an uncertain attempt stays failed or timed out, and you can insert it again yourself. If the connection drops while a claim is being saved, that row can stay doing until its 30 minutes run out.

Set it up from an agent

An agent in one of the project's terminals can do all of the above with the connecto works command, without the sheet: ask it to "set up an agentic work that …". It reaches only its own project. The built-in Connecto package gives Claude and Codex the agentic-works skill, which walks through these steps.

connecto works show                                   # link, work types, last outcome
connecto secret request WORKS_DB --agentic-works --reason '…'
connecto works test-db --secret WORKS_DB              # each step, changes nothing
connecto works link --secret WORKS_DB --create        # or without --create to validate
connecto works publish summary --file summary.json    # {"instructions", "schema", "setup"?, "prepare"?}
connecto works test summary --prompt 'the README'     # queues a job, prints its id
connecto works job 42                                 # status, result JSON, reason

What an agent may do

Linking a database, publishing a type, running setup, queuing a job and importing a key make Connecto run commands, start agents or replace a credential with your rights. From the command line only an agent that Connecto started in Bypass mode may do them: it can already run any command without asking, so this gives it nothing new. Connecto reads the mode from the agent's own launch, not from anything the agent says.

  • An agent started in Auto or Prompt mode, or a shell, may only read: show, check, test-db, guide and job. When it publishes, nothing is published: Connecto only records its terminal as the work type's author, so that the sheet can import its reply. The agent ends its turn with the definition as its reply, and you click Import author reply for that work type in the sheet, review it and publish it. Linking, setup, jobs and key imports it leaves to you.
  • The agent of a job, in an agentic_works_… terminal, can never change Agentic Works: its prompt comes from the queue. Nor can a terminal it started with connecto add, or one those started: Connecto marks each when it makes it, in the project's saved terminal list, and the mark stays whoever closes the job's terminal, through restarts and a new parent.
  • The mode is the one of the very session that runs the command: a restart in another mode does not carry it over.
  • Each connecto works command that changes something goes in the audit log with the terminal that ran it.
  • Under Pause, only the reading commands work, and test-db only for the linked database.

Secrets

  • Secret values never reach the agent. It asks you for a connection string with connecto secret request <NAME> --agentic-works. You type it in Connecto, and it is kept as an Agentic Works database secret of the project.
  • A Cloud SQL password is asked for by Connecto itself: the first test-db or link for a user and instance shows you a request naming both. That password is used for that user on that instance only, never as a connection string, and no other secret stands in for it.
  • connecto works key-import <file.json> (Bypass only, since it replaces the key kept for that account) reads the key file with the terminal's own rights, as the agent could, and only a regular file up to 64 KiB. The key goes into the vault and is never printed.
  • Replies never show a vault value: results, reasons and notices are cleaned of them, and JSON stays JSON.

For Google Cloud SQL, connecto works guide --cloudsql … prints the setup steps above and the link command that fits them. link takes --cloudsql, --database, --user, --key or --adc, --ip public|private|psc and --iam. connecto works check validates a definition without publishing it: a definition is the same JSON object an authoring session replies with. A type with a setup command starts setup in its terminal, as from the sheet. publish waits a few seconds for it, then says that setup is still running, and connecto works show tells when the type is published.

Who may write to the queue

Writing a job starts an agent in your project. It runs with the project's launch mode, including Bypass when the project uses it, and can read and change the project's files. Give write access to the queue only to programs you would trust with that.

  • Producers use the role that owns the queue, or a connection you control that runs as it. Connecto checks the grants before every claim and stops if any other role can write.
  • Readers that only need results can be granted SELECT.
  • A job's prompt reaches a prepare command only as standard input: never as an argument, an environment variable or a file name.
  • Pause stops a running job and keeps new ones from being claimed.
