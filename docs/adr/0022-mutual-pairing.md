# ADR 0022: pairing by two codes, both ways

**Status.** Replaces the one-sided pairing in ADR 0017 ("Pairing with a six-digit code"). The rest of ADR 0017 stands: the transport, the SSH-key authorization, the Gate and the audit log.

**Context.** One machine showed a code and the other typed it. The pairing gave the host an `authorized_keys` line and the client a `known_hosts` pin, and the two machines did not agree on what they had: the host did not know the client's endpoint, and a revoke on the host did not close a live session. Both machines should now show a code, each type the other's, and end up with the same kind of record.

**Decision.**

- **Codes.** Each machine shows its own code of eight digits (`PAIRING_CODE_DIGITS` in connecto-core, the one constant) when the user starts pairing. A code works for two minutes from when it is shown (`CODE_LIFETIME`). It is not reused: a new pairing makes a new code.
- **Keys from both codes.** When a machine has both codes it computes, in canonical order (the lower code first, as strings of equal length), `K = Argon2id(lo "|" hi)` with the production cost (256 MiB, 8 passes, about 0.7 s in release). Then `rendezvous = HMAC(K, "rendezvous")` is the secret of a temporary iroh endpoint, and `pake = HMAC(K, "pake")` is the SPAKE2 password.
- **Roles from the codes.** The machine holding the higher code listens on the rendezvous endpoint (`PAIR_ALPN`); the one holding the lower code dials it, retrying until the listener is up or its code expires. Equal codes have no roles and are refused on both machines. Entry order does not matter: a machine that has both codes and no peer yet waits.
- **Exchange.** Over that connection: SPAKE2 (`spake2` crate, Ed25519 group), then HMAC key confirmation both ways. Each MAC covers a transcript of the rendezvous id, the TLS session's exported binding and both PAKE messages. Then each side sends its offer: its device name, its real endpoint id, its relay and addresses, and a fresh per-pair Ed25519 public key for the other side to authorize. Each offer is signed with the endpoint key of the id it names, over the transcript, and both sides verify the signature against the id before they use the offer. So the codes alone never make a machine the id of another. The listener also checks that the dialer's id is the machine the connection came from; a machine offering its own id is refused. Every wire value is validated when it is decoded: relay (http or https, printable, no spaces), addresses (socket addresses only), device name (no control characters), key (one valid OpenSSH key), and all sizes and counts are capped.
- **Naming, staging and commit.** After the exchange each user names the other machine, locally; the name is the user's, not the wire's. Then, in order: the guard is asked (Pause refuses here); the record is staged durably (below); the **intent** is exchanged: each side sends a MAC over the transcript and both offers saying it will keep the pairing, and waits for the other's. Until this side sends its final word, a cancel (or a refusal) ends the pairing on both sides, and nothing is kept. The **commit point** is passed when this side records its final word as sent and sends it; from then a cancel is not taken. Each side keeps the pairing when the other side's final word arrives. The final wait is at most 20 seconds, since nothing can be cancelled by then. The naming window is two minutes.
- **What is saved, durably.** Staging writes, in this order, each step to disk before the next: (1) an entry in `<data>/remote/staged.json`, with the machine's previous `authorized_keys` lines and host line, so they can be put back; (2) the new key, in the Keychain under `remote.pair.<id>.staged`, not yet the key this machine dials with; (3) the new `authorized_keys` line; (4) the new `known_hosts` entry. Its status moves `staged`, then `sent` (before the final word leaves), then `kept` (when the other side's final word has arrived), and only then is the staged key moved to `remote.pair.<id>`, the `authorized_keys` line committed (see the re-pairing rule below), and the entry removed. A crash or a failure at any step is undone at the next start (`staging::recover`): every entry that is not `kept` is rolled back, restoring any previous record for the machine, and a `kept` entry is finished. The staged key of a `staged` or `sent` entry is never let in for a session.

- **The staged mark.** The new key line's comment is `connecto-id=<id> (staged <date>)` until the commit, and a kept record rewrites it to `(paired <date>)`. Sessions never accept a marked line, whether or not `staged.json` is readable.
- **A re-pairing keeps the old key until the commit.** Staging adds the new marked line and leaves the machine's previous line in place, so the machine can still open sessions while the pairing is under way (live sessions are not touched either). The commit writes `authorized_keys` once: the new line loses its mark and the lines it replaces are removed. A rollback restores the previous lines as before.
- **Past the commit point nothing is undone in the session.** If `keep` fails after the final word has gone, the entry stays `kept` and is finished at the next start, rather than rolled back, so this side does not undo a pairing the other side may have kept.
- **A damaged record file.** If `staged.json` cannot be read or parsed, or it is missing while a marked key line exists, nothing in it is trusted, and the start-up recovery (`staging::recover`, the sweep) decides from the surviving files alone. A machine is *finished* when `authorized_keys` has a committed line for its id, `known_hosts` has its host, and the Keychain has its dial key `remote.pair.<id>`. Every other key line is removed (hand-added keys included, and lines with options, which are never honoured). Comments, blank lines and the keys of the older flow (no id, a `(paired` comment) are kept. For an unfinished machine its host, staged key and dial key go; for a finished one a leftover staged key goes and its previous key stays. A copy of the key list and host list is kept before they change, and the damaged file is renamed to `staged.json.<ms>.damaged` (owner-only) only after the sweep has finished, so a failure at any step is retried at the next start. A Keychain or file error stops the sweep with nothing let in. The user sees a notice (the remote view's `last_error`) naming the machines to pair again and the kept files.
- **Identity.** A machine's id is its real endpoint id as 64 hex digits. Keys from the older flow have no endpoint id and appear as `legacy:<SHA256 fingerprint>`.
- **Disconnect.** `disconnect_machine(id)` removes the machine's `authorized_keys` line first (so no new connection gets in), closes its live inbound session, removes its `known_hosts` entry and stops its outbound link, then deletes its Keychain key. The other machine is not notified. Its next attempt is refused by the host (`NotAuthorized`), and its view shows the machine as refused until its user removes it.

**What the codes protect, said plainly.** The codes are the only secret: eight digits, about 26.6 bits each (`PAIRING_CODE_DIGITS`; six digits was the first design and is no longer used).

- *Without either code* nothing useful can be done. The rendezvous id is derived from both codes, and the offers are signed by endpoint keys that the attacker does not hold.
- *With one code* (read off a screen, say) the attacker needs the other. The rendezvous id `R` is an offline oracle: each candidate costs one Argon2 evaluation (about 0.7 s and 256 MiB on a release build) and a comparison with `R`. Anyone who sees `R` on the relay (the relay operator, or a network observer of the relay's endpoint ids) can run that comparison offline. All 10^8 candidates cost 7 x 10^7 core-seconds: about 19 hours on 1,000 cores, about 65 hours on 300. Finishing inside one 120 s window needs about 580,000 cores (about 140 TiB of memory). The five-entry and start limits are local and do not slow an offline search. Seeing `R` needs no relay token and no dial.
- *What such an attacker gains, and when.* Recovering the second code does not by itself give a session. The attacker must become an active party in a live pairing, and two orders are possible:
  - *Listener squat.* The dialer's attempts to reach `R` are visible on the relay before the listener is up. An attacker who has recovered the codes can listen on `R` first and take the listener role. The dialing machine then sees an offer from the attacker, signed with the attacker's own key (the signature must match the id the offer names, so the attacker cannot present another machine's id). The dialer's user is asked to name it, and the record is for the attacker's id. Existing records are never replaced, since they are keyed by ids the attacker does not hold.
  - *Dialer-first race.* If the attacker recovers the codes after the listener is already up, it must reach the listener before the legitimate dial, within the listener's window.
  - Once the legitimate connection has been made, or the window has closed, recovering the codes gains nothing. The listener has closed. The PAKE and the offers ran inside TLS, which the relay cannot read and which has forward secrecy, so a recording gives no transcript to test guesses against. Only `R` remains, and `R` leads nowhere once the pairing is over.
- *The realistic harm* is an extra machine, with a name the user accepted, that the attacker controls. That machine then has the same authority as any paired machine (ADR 0017): a key that can open sessions to this host.

**Decided: eight digits.** The offline search was the exposure, and six digits (about 20 bits) left one known code a search of 10^6 candidates, which a few hundred cores finish in under an hour. Eight digits make the same search about 100 times longer (see above). The Argon2 cost is unchanged, as the decision required. Raising it (for example to 1 GiB and 8 passes) would multiply the cost per guess by a constant four and is a possible later step. It does not change the order of the search.

**Residual risk, said plainly.** The final word is a two-generals step. If this side sends its final word and the other side never receives it, the other side rolls back while this side keeps the pairing; the same happens if this side crashes after recording `sent` and before it hears back, since the next start rolls back. The user then sees a machine that connects one way only, and removes it. Within those cases the sides end with different outcomes only in this documented way; every other path ends with both sides keeping or both rolling back. A cancel before the final word is sent leaves nothing kept on either side.

**The release guard (`test-relay`).** `test-relay` switches off the relay's certificate check. It enables iroh's `test-utils`, and it is reached only through connecto-net's own dev-dependency. The compiler cannot tell the shipped build from `cargo test --release`, because both can carry the feature, so no compile-time refusal is possible without breaking release tests. The guard is therefore enforced by the build: `scripts/release/check-release-features.sh TARGET` runs `cargo tree --edges features --locked --target TARGET -p connecto-app -p connecto-hook` and fails if the output names `test-relay` or iroh's `test-utils`. Every release script runs it before building, and the release workflow runs its self-test (`--self-test`, which proves the check trips on the feature). A runtime refusal inside the library was considered and rejected: it would need a process environment setting that the tests have to set, and it adds nothing the feature graph does not already guarantee.

**Limits.**

- The host accepts one inbound peer at a time, as ADR 0017 says (`HostService` refuses a second with `Busy`). The machines list can show an inbound link for each machine, but only one can be live.
- A pairing has one name per machine for each side. Renaming is by `rename_host`.
- The relay token is still not in the binary and pairing does not carry it.

**Alternatives.** A one-code flow where the second code is a confirmation (rejected: the second code would still be guessable, and a machine would still act on a code its user cannot check). An explicit fingerprint comparison on both screens (kept as the Advanced path, where the address is typed in by hand).
