# ADR 0017: remote sessions over iroh, authorized by SSH keys

**Context.** One Connecto should be able to show and drive the terminals of another on a different machine. Terminal input must feel local, so the path has to be a direct QUIC connection when one can be had, and a relay only when it cannot. The relay is self-hosted and not public.

**Decision.**

- **Crate.** `connecto-net` holds the wire types, the handshake, the host and client halves and the iroh transport. It depends on `connecto-core`, `connecto-gate`, `connecto-audit`, `connecto-term` and `connecto-redact`, and nothing depends on it yet.
- **Async stays inside it.** ADR 0002 stands for the rest of the app. `IrohNode` runs a current-thread tokio runtime on one thread named `connecto-net`. Everything outside sees the blocking `Connection` and `Stream` traits and crossbeam channels. Tokio is not a dependency of any other crate.
- **Transport.** iroh 1.4 (QUIC, dialed by endpoint id, hole punching, relay fallback). The endpoint uses the `Minimal` preset, so it contacts no n0 relay and no n0 DNS. The relay URL and its access token are configuration (`IrohConfig`, set in Settings), never constants; the planned relay is `https://relay.connecto.studio` (behind Caddy on 443, with QUIC address discovery on UDP 7842, which the client derives from the URL's host and the default QUIC port). It is not deployed yet and nothing is tested against it. Without a relay URL the endpoint is direct-only. Each endpoint has a device key (Ed25519, 32 bytes) kept in the Keychain beside the relay token (`secrets.rs`), never in a file in the data folder and never printed (`IrohConfig`'s `Debug` hides both, and `describe` also runs `connecto-redact`).
- **Streams.** One bidirectional stream for control and authentication, and one per attached terminal. Frames are a `u32` length, a tag and fixed fields, with a 256 KiB cap checked before the body is read. Terminal output is numbered by byte offset. The host keeps a 1 MiB ring per terminal; a client resumes at its offset, or, if the ring no longer holds it, is repainted from a description of the current screen. The client keeps its own emulator, so drawing is the local code.
- **Authorization.** The transport identity is the device key. Authorization is an SSH key: the host sends a nonce, the client signs, through ssh-agent, an SSHSIG in the namespace `connecto-remote-auth@v1` over the nonce, both endpoint ids and a value exported from the TLS session. The host accepts only a key in its own Connecto `authorized_keys` file, read at each connection. Lines with options are not honoured and so do not authorize. The client pins the host's endpoint id by display name, as `known_hosts` does, and refuses any other machine before it signs. No terminal stream is accepted before the handshake ends.
- **Safety.** Hosting is off until it is turned on. A peer is a distinct actor, `remote`, in `connecto-gate`: attach is audited durably, typed input is audited as a count and a hash per second and never as text, and Pause refuses input and resize. One peer at a time. The `connecto` bridge socket is not reachable from a remote peer: it is a local Unix socket, and the host never forwards bridge frames.
- **Addressing.** Terminals are `(host, terminal)`. `localhost` is reserved for the local machine; every other host is a unique, renameable display name saved with its pinned endpoint id and reach hints (`trust.rs`).

**Alternatives.** A WebSocket relay for all traffic (always one hop more, and the reconnect and encryption are ours to write); Tailscale (a daemon the user must install, no per-session identity); SSH itself as the transport (no hole punching or relay of our own, and no multiplexed terminal state).

**Consequences.** The iroh and ring dependencies add build time. A paired machine can type into every terminal of the host, as the user could: there is no sandbox (ADR 0013) and the tools run with approvals off, so an authorized key is full access to the account. A pasted wrong line in `authorized_keys` that is a key lets that key in.

**Wiring (second slice).**

- **Rings.** `LiveSession::start_tapped` takes an `OutputTap`; the launcher asks one process-wide `TapFactory` (`launch::set_tap_factory`, set by the app before the workspace starts) for a tap per terminal, keyed `<project id>/<terminal id>`. Every launched terminal gets a ring (1 MiB, memory only) whether or not hosting is on, so turning hosting on reaches terminals already running. A restart makes a new ring and closes the old one, which ends any peer's stream on it; the peer attaches again and is repainted.
- **Hosting is off by default.** `<data>/remote/settings.json` holds `enabled` and the relay URL. Off, the endpoint is built with no ALPN, so a peer that dials it is refused during the TLS handshake. The device key and the relay token are in the Keychain. The keys that may connect are `<data>/remote/authorized_keys` (0600), read at each connection.
- **Dependency rule.** Only `connecto-session` may depend on `connecto-gate` (`dependency_rules` test). The guard trait (`RemoteGuard`) is in `connecto-core`; its Gate-backed implementation (`RemoteGate`) is in `connecto-session`; `connecto-net` sees only the trait.
- **Reconnect.** A `HostHandle` per saved host runs a supervisor: dial, authenticate (each ssh-agent key in turn), list, attach, and on a drop dial again after 1 s, doubling to 30 s. Each terminal's `RemoteSession` outlives connections and resumes at its last applied byte; the host repaints only if its ring no longer holds that point. A refusal that waiting cannot fix (no key allowed, another machine answered) stops the retries until the user asks to connect.
- **Hosts.** A saved host has a unique, renameable name and a pinned endpoint id (`known_hosts`); `localhost` is reserved. Adding one shows its fingerprint to compare before anything is saved. In the window a remote host's projects are shown as the host lists them, each drawn like a local project: its terminals are grouped by project, children sit under their parent, and the tree, tabs and panes are the existing code. A project shows once it is open and set up, even with no terminal. Adding, closing, restarting and renaming a host's terminals go through the wire; continuing from history and reading transcripts do not.
- **Projects and nesting (protocol 2).** A host's list carries its open, set-up projects (`ProjectInfo`: canonical id and name) in its order, at most `MAX_PROJECTS` (64), then its terminals, at most `MAX_LISTED` (64), each of a listed project. A project with no terminal yet is listed and takes its first terminal by `Add`. A peer granted `FEATURE_TERMINAL_IDS` (only with `FEATURE_BACKGROUND`) gets `TerminalListIds`: the extended list plus each terminal's id on the host (`claude-12`), which it shows in place of the wire number. Such a peer is sent every terminal of a listed project, stopped ones too (one that has not run since the host started gets an empty ring), so it sees and can start what the host's sidebar shows; it opens no stream for one that has never run until a list says it runs. Starting one is refused where the host's window would refuse it (the agent deactivated there, or off in the project's settings). Any other peer is sent, as before, only terminals that have run since the host started and the restored chat; the never-started ones are left out before the cap, so an older peer keeps every terminal it saw. `TerminalInfo` carries the project id and name and the parent's wire id, which is a top-level terminal of the same project in the same list.
- **The rule (identity form).** An operation from a connection (attach, input, resize, rename, restart, close, add) is allowed only on a terminal or project that the latest list sent to THAT connection contained, identified by its stable identity, and checked at dispatch time. A terminal's identity is its wire id: the registry gives each terminal entry (its project and entry id) one number for the life of the app and never gives that number to a second entry, so a terminal that was closed and a new one created are different identities, and an old grant never matches the new one. A restarted entry is the same entry and stays granted: a restart changes nothing the rule names, and the peer could restart it itself. A project's identity is its folder id, so a project closed and opened again is the same project and stays granted. The grant is the connection's own latest list (`Shown`), so a terminal sent to another connection, one past the cap, or one never listed is refused.
- **Dispatch.** `HostService::authorize` is the only code that makes a `Right`. Every send to the peer about a target goes through `deliver`, which checks the right and enqueues while the connection's listing is held. Sends never wait: a full queue fails that stream, which then ends (the peer is not reading), so no lock is held across a blocking send. Session actions go through `act_held` in the same way. Each stream checks its right on every pass of its write loop, so a revoked stream is told `NoSuchTerminal`, ends, and releases its size lease.
- **Close takes its children, decided where it runs.** A peer's close is `TerminalsControl::close_within(entry, allowed)`: the registry works out the subtree (every entry under the target, listed or not) inside its own worker, at the moment the close runs, and closes only if every member is in the connection's listed entries of that project. A child added after the list, even while the close waits in the queue, is in the subtree and is refused, with nothing closed. Local closes cascade as before. `RemoteTerminals` (the client view) refuses by default.
- **Backpressure.** A send never waits. `NetError::Full` means the peer's queue is full (it is not reading yet); `Closed` means it is gone. Control replies (`Size`, refusals, status) that cannot be queued end the stream. Output and repaints are retried: each attempt checks the right under the listing, enqueues without waiting, and on `Full` waits (2 ms) outside any lock and tries again, with the cursor advanced only once the bytes are queued. A slow but live peer therefore receives every byte in order, and a revoke during the wait stops the output at the next attempt. Flow control stays byte-based (the 512 KiB unacknowledged window), so a peer that never acknowledges stops the terminal's output without any queue or lock being held. Output waits end on connection stop, reader end, revoke, or the attached ring closing; a ring that closes retires the stream (the peer is told for up to 200 ms, then the stream ends) so the replacement attaches. Every client reader and writer checks its link and its session attachment on every pass, idle or not, and ends with them; a re-attachment closes the link it replaces. The client applies the same rule to its input, resizes and acks: a full host queue is waited for, and a genuine failure, or 30 s without room, marks the link closed so the supervisor redials. Opening a stream and accepting one never wait either.
- **Numbers run out safely.** Wire ids come from a checked counter. When the counter is exhausted a new key gets no number and its terminal is not offered; no number is ever reused or wrapped.
- **Re-attach refusals.** A re-attach the host refuses (`NoSuchTerminal`) is not sent again until the next list: the supervisor remembers the refused terminals for the current listing and clears them when a list arrives.
- **Restarts.** When a terminal's stream ends because it was restarted or closed on the host, the supervisor attaches it again at once, from the top, without waiting for a list: its grant is unchanged. A peer's own restart also triggers a list, as an optimisation only. Other changes made on the host (an add, a start) reach the peer on the next list: the supervisor lists on connect and every heartbeat (3 s by default).

- **Call sites that send to a peer or act on a terminal** (all in `host.rs` unless noted): `control_loop` `TerminalList` (builds the listing and the connection's grants) and `ManageResult` (outcome of a request; no terminal data). `manage` (authorize, guard, re-check, `close_within` for a close, registry). `terminal_stream` refusals, the attach re-check, `Attached` and `Status` (via `deliver`), the repaint (`act_held` for the capture, then `deliver`). `read_peer` input (`holds`, guard, `act_held` for `send_input`), resize (`holds`, guard, `act_held` for the lease, the resize and the read-back, then `deliver` for `Size`), and refusals. `write_peer` the per-pass check, `Output`, `Status`, the ring-closed refusal and repaint. Refusals reveal nothing and only end or refuse a request, so they are sent without a right; lease release needs none either.
- **What the registry must guarantee** (for the rule above): an entry number is never reused for another entry (`WorkspaceTerminals::id_of`), and a project id is its folder hash. Registry actions take the entry or project the right names, so a new entry under an old number cannot be reached through an old grant. The registry's own generation counts and the checked-change methods were removed in the fifth round; the session side is back at HEAD.

- **What the receiver accepts.** It refuses a whole listing, never part of it, when a project id is not lowercase ASCII letters, digits, `-` or `_`, a project id is listed twice or with two names, a terminal id repeats, or a terminal names a project the listing does not give. Projects may share a name. Labels are made unique: a name that is unique shows as it is; when labels would be equal, each project in the clash shows `name (id)`, and the check repeats until no two labels are equal, so a name a peer chooses cannot forge another project's label. Each label stays within 120 characters. A refused listing leaves the last accepted one in place. Names from a peer are cleaned for display: control characters, line and paragraph separators and the Unicode bidi controls become spaces, and 120 characters at most.
- **Versions.** Protocol 2 does not talk to protocol 1: a peer on the other version is refused with a message to update both machines to the same Connecto version, so both sides must be updated together.
- **Resize.** The remote peer is the main user, so once its window shows a terminal it has that terminal's size until it detaches (`host::RESIZE_POLICY`, the one place this is decided). A peer attaches every terminal in the background, so an attach alone takes nothing: the size moves to the peer at its first `Resize`, and a reattach repeats the last size its view asked for. Its resizes drive the PTY through `TerminalSession::resize_remote`; the host window's own layout calls `resize`, which only remembers the wish and changes nothing; the host view draws the terminal at the peer's grid. When the peer detaches, for any reason (`SizeLease` drops), the last local wish is applied and the host view has its size back. The last click decides: a click on the terminal in the host window takes the size back (`TerminalSession::claim_local_size`, counted by `local_size_claims`), applies the last local wish, and the peer's stream, seeing the count change, drops its lease and sends the peer `Size` with the host's grid before any output that follows. A click in the peer's window asks for its size again, and that `Resize` takes the lease again.
- **A size at its byte.** A peer must take each size exactly where the host's screen took it: Claude Code redraws with cursor-up and erase-line, so output the host drew at one size and the peer draws at the next lands on the wrong rows (seen as piled copies of its slash menu after a burst of resizes). The session therefore resizes its screen through its output tap (`OutputTap::resize`), and the ring marks the size at the current byte under the same lock that feeds the screen (`Ring::resize_with`, which never waits: a ring busy with output answers `Retry`, as a busy screen does, so a window resize does not block); a session marks its first size before any output. The stream's writer reads marks and bytes in order and never reads bytes across a mark it has not passed (`Ring::read_wait_at`), sending each mark as the existing `Size` message, so the wire and older peers are unchanged. A resume is told, in `Attached`, the size in effect at its byte, and is repainted instead when a size was marked exactly at that byte (the peer may or may not have taken it, and a shrink and grow back there loses cells a resume would keep) or the marks up to it were dropped; a repaint carries the size of the screen it captured, and the writer goes on from the capture's byte and mark. The ring keeps at most 1024 marks; a reader behind a dropped one is repainted, as one behind dropped bytes is. A ring with no marks (a session with no tap) keeps the earlier rule: the size the session last applied is sent before the output that follows. A repaint leaves the peer's screen as the host's for later resizes too: blank cells after a row's text are not written (written, they reflow as content), and a row the terminal soft-wrapped is wrapped again, so both screens reflow alike.
- **Repaint** carries mouse (click, drag, motion, SGR, UTF-8) and focus reporting, now tracked by the emulator. It does not carry scrollback, the scroll region, tab stops, or origin and autowrap modes.

**Pairing with a six-digit code (superseded by ADR 0022, which pairs by two codes, both ways).**

- **Flow.** The host chooses Pair a device (Settings, Remote access) and shows a six-digit code, valid for two minutes and for one device. The other machine chooses Add host, types a name and the six digits, and the host appears in the switcher and connects. Nothing is copied: no address, no public key, no `ssh-add`. The address and SSH-key way stays as Advanced.
- **Hosting.** Pairing turns hosting on and leaves it on, because it ends with the other machine connecting to this one. The pairing screen says so.
- **Rendezvous.** Both machines turn the code into the same iroh secret key (Argon2id, 256 MiB, 8 passes, fixed public salt, about 0.7 s on an M-series Mac in a release build; the production cost is not asserted in the debug test run). The host binds a temporary endpoint with it, using its own protocol name (`PAIR_ALPN`) so it refuses every normal session; the client computes the endpoint id and dials it through the relay by id. The relay sees only endpoint ids. This works with no other discovery, as the relay-only test shows (dial by id plus the relay URL).
- **Authentication.** Inside the connection both sides run SPAKE2 (RustCrypto `spake2` 0.4, MIT or Apache-2.0) keyed by the code, with the two endpoint ids as identities, then confirm the key with HMAC-SHA-256 over a transcript that includes the TLS-exported binding. Under that key the client sends its device name and a public key, and the host answers with its real endpoint id, relay and addresses. Both messages carry a MAC.
- **The key.** The client makes a dedicated Ed25519 key on first pairing and keeps it in the secret store (the Keychain, or the data folder in dev mode). It signs the normal SSHSIG challenge with an in-app signer, so the handshake is unchanged and `authorized_keys` stays the one source of truth. The host appends the key once with the comment `<device> (paired <date>)`. Paired devices are listed in Settings and revoked by removing the key.
- **Burning.** One connection spends the code, whatever its outcome. The code also expires, and asking for codes is limited (one every three seconds, eight in ten minutes).
- **What the code protects, said plainly.** The code is the secret, and anyone who learns it within its two minutes gets full control of the host's terminals: the host screen says so. A wrong code never reaches the host (it derives a different endpoint id, so there is nobody to connect to), which means the PAKE's "one online guess" limit is not what stops guessing. What stops it is the cost of deriving a key per guess: someone who can watch endpoint ids on the relay, or probe it (the relay requires its token for that), can try all million codes, each costing 0.7 s and 256 MiB, against a two-minute window. The PAKE and the confirmation make sure that a party without the code ends at once, that the exchanged data cannot be changed in transit, and that the code is burnt by any attempt that does reach the host.
- **Safety.** The pairing endpoint accepts nothing but the pairing protocol. Accepting a key passes the Gate and the audit log as the `remote` actor (action `pair`) and is blocked by Pause. The code is never logged and never in a `Debug` print.
- **Default relay.** `https://relay.connecto.studio` is the default and stays configurable (an empty setting means no relay). The relay token is not in the binary: both machines need it before they can reach the relay, so pairing cannot carry it (open decision).
- **Paired-key rule.** The client tries its paired key before ssh-agent's keys.

**A host project's history and settings (2026-11).**

- **Ask.** `ProjectAsk { project, ask }` on a stream of its own; `ask` is JSON (`connecto_net::project_panels`), so either side can add fields. It reads the project's history, a transcript, its package settings and its Agent Token Optimization, or changes them (Continue, settings, Refresh, analyze/apply/undo/compaction). It is answered as a `FileRead` is (`FileStart` with an empty path, then chunks, at most 4 MiB), with `FileRefused`, or with `Denied`. A host from before it answers `Denied(Protocol)`, and the window says to update Connecto there.
- **Rule.** Only for a project of the connection's latest list, while hosting is on, and only once the guard has let the ask through as `project-<ask>` (audited; Pause refuses every ask, reads included). The right is checked again after the guard. A peer's settings cannot name a package the host does not have, and Continue respects the project's allowed tools.
- **Not shared.** Project Memory and a project's own model providers are set up on the host; the remote sheet says so.
- **Operations (2026-11-22).** A peer views, approves and runs a host project's operations (ADR 0031) as the host's person can: `ProjectAsk::Ops { after }` answers the view with each operation's `op.json` and script exactly as read, in slug order after the cursor slug, in pages measured as sent (escaped JSON, within the 4 MiB answer, at least one operation each). The peer reads them to the end, each page after the last slug it has (an operation removed between pages moves no other), and refuses more than a project's 100 operations, a page out of order, or an empty one that says more follow; and `ProjectAsk::OpsAct` carries one action to the host's `OpsControl::act`. The guard records each as `project-ops-<verb>` on `<project>/<slug>`, and Pause refuses them. The peer reads what it shows from those files and hashes them itself, so the hash it approves or runs is the one of what it showed; the host refuses it when its files no longer have it. Arguments of a run are checked by the host as its own dialog's are. A host from before this answers that it does not know the ask, and the tab says to update Connecto there, with no control to change anything.

- **Secrets (2026-11-22).** A peer lists and changes a host project's own secrets, and answers its terminals' requests for one (`ProjectAsk::Secrets` and `SecretsAct`). It learns of waiting requests through `Message::SecretAsksProbe`, which returns those of the projects in its latest list. The value travels only inside this link and never comes back. The guard records `project-secret-<verb>` with the secret's name, Pause refuses every ask, and a host from before this is told apart so the window says to update it. See ADR 0027, "From a paired machine".

- **Project groups (2026-11-22).** A peer shows the host's sidebar groups as the host has them. `Message::GroupsProbe`, asked at each heartbeat, returns the groups in the host's order and the group of each project in the connection's latest list (never a project not sent). In the peer's sidebar each group shows over its projects, with ungrouped projects after. The groups are under ids of the peer's own (`remote-group:<host>:<id>`), fold there, and are created, renamed, deleted and filled only on the host. Folding is each window's own and is not shared. A host from before this answers `Denied(Protocol)`, and its projects show flat, as before.

**Files a host offers (2026-11).**

- `connecto send-file <path>`, run by an agent on the host, offers the file to the machines viewing that Connecto that show the terminal's project, for ten minutes (`connecto_core::offers`). A peer can download only an offered file, never name another. The offer is checked when made (a regular file, at most 64 MiB, not under `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/Library/Keychains` and similar) and when sent (the same canonical path, opened without following a link put in its place).
- `OffersProbe` / `Offers` list them (asked at each heartbeat); `OfferRead { id }` sends one as a `FileRead` is, after the guard (`read-offer`; Pause refuses it). The window shows a strip: Download saves to Downloads under a name not taken there, then Open and Show in Finder.
- Cmd-click on a path in a remote terminal still previews and downloads files inside the terminal's project folder (`FileRead`); a file elsewhere needs an offer.

**Not done yet.** Mouse forwarding from the window (the UI still selects on drag), a host-side view of who is connected beyond a status line, and a measured relay latency budget.
